# 平台后端架构与集成开发基线

> 状态：已确认
>
> 用途：作为后续开发、评审、接口对接与部署的共同基线。新增功能不得绕过本文定义的边界；如需变更，必须先更新本文并记录原因。

## 1. 系统定位

本平台是 ERP、CRM 与百应之间的集成中台，而非单纯的百应前端管理工具。

平台负责：

1. 接收 ERP 和 CRM 发起的任务、客户名单与业务参数。
2. 使用全局话术变量映射，将业务参数转换为百应需要的 `properties`。
3. 调用百应 API 创建、管理任务并导入客户。
4. 接收百应回调，统一标准化后回传 ERP 和 CRM。
5. 提供运营后台、审计、失败重试、死信处理和人工重放能力。

## 2. 已确认架构决策

### 2.1 前后端分离

前端、后端和异步任务必须独立部署、独立演进。

```text
console.example.com     前端运营后台
api.example.com         平台 API
worker-sync             定时巡检、异步导入、回调投递
PostgreSQL              核心业务与集成事件数据
R2                      文件、导入包和导出文件
```

当前前端原型可以继续维护在现有仓库，但正式开发时必须将运行时职责分离。

### 2.2 技术选型

| 层级 | 选型 | 说明 |
| --- | --- | --- |
| 前端 | React + TypeScript | 运营后台，不承载外部密钥或业务编排 |
| 后端语言 | TypeScript | 与前端共享类型，降低三方字段转换错误 |
| API 服务 | Cloudflare Workers 或容器化 TypeScript 服务 | 对外 API、鉴权、编排、接口代理 |
| 主数据库 | PostgreSQL | 任务、映射、事件、投递与审计的系统记录库 |
| ORM / 迁移 | Drizzle ORM | 类型化数据访问与版本化迁移 |
| 异步消息 | Cloudflare Queues | 导入、回调投递、重试、削峰 |
| 定时任务 | Workers Cron | 百应变量巡检与过期检查 |
| 文件对象存储 | Cloudflare R2 | 凭证、导入文件、失败明细和导出文件 |
| API 契约 | OpenAPI 3.1 | ERP、CRM、前端共用的接口规范 |
| 密钥管理 | Workers Secrets / 部署平台 Secret | 密钥不可进入前端或仓库 |

## 3. 逻辑架构

```text
ERP（.NET） ─┐
             ├─→ 平台入站 API → PostgreSQL → Queue → 百应 API
CRM（PHP） ──┘                         │
                                      └─→ Queue → ERP / CRM 回传接口

百应回调 ─────────→ 平台回调 API ──────┘
```

ERP 使用 .NET、CRM 使用 PHP 不影响平台实现。三方统一采用 HTTPS、JSON 与 OpenAPI 契约；平台内部不依赖对方运行时语言。

## 4. 仓库与模块边界

正式开发推荐拆分为：

```text
outbound-console-web      React 前端运营后台
outbound-platform-api     平台后端 API 与异步消费者
outbound-contracts        OpenAPI、DTO、事件模型和 JSON Schema
```

后端模块必须按职责拆分：

```text
api-contract/        OpenAPI、JSON Schema、共享 DTO
integration-ingress/ ERP / CRM 入站接口、鉴权与幂等
baiying-adapter/     百应签名、变量同步、任务与名单接口
mapping/             全局变量映射、版本与快照
task-orchestration/  任务创建、名单导入、状态流转
callback-dispatcher/ ERP / CRM 回传、重试、死信与重放
audit/               请求、事件、投递记录与审计
```

约束：

1. 页面只可调用平台 API，不可直接调用百应、ERP 或 CRM。
2. `baiying-adapter` 是唯一允许读取百应密钥和 Access Token 的模块；百应主动调用统一采用最新 OAuth v2，不保留旧版 HMAC/v1.25 适配器。
3. ERP/CRM 字段差异只能存在于各自适配器中，不可散落在任务或映射业务代码中。
4. 映射、任务、回调和审计模块不得直接依赖前端实现。

字段映射属于第 3 条的明确例外边界：仅对百应 4.10 接口返回的话术变量，在 `mapping` 模块内保存 ERP 与 CRM 各自的取值字段；它不是全量业务字段字典，也不得扩散到其他业务模块。

## 5. API 契约与版本规则

### 5.1 统一协议

```text
传输协议：HTTPS
报文格式：application/json
接口前缀：/api/v1
契约来源：OpenAPI 3.1
```

所有对外接口和回调事件必须包含：

```text
event_id          全局唯一事件 ID
request_id        链路追踪 ID
idempotency_key   幂等键
occurred_at       事件发生时间
schema_version    报文版本
```

### 5.2 入站接口原则

ERP/CRM 调用平台时：

1. 校验签名、时间戳、权限和报文 Schema。
2. 以 `source_system + idempotency_key` 检查重复请求。
3. 先持久化请求和待处理事件。
4. 耗时操作进入队列。
5. 接口返回 `202 Accepted` 及平台请求 ID。

同步接口仅做轻量校验；不得在用户请求链路中等待百应的长耗时操作完成。

### 5.3 回调接口原则

平台回传 ERP/CRM 时：

1. 先写入 `integration_event`，再进入投递队列。
2. 接收方返回 `2xx` 才视为投递成功。
3. 非 `2xx`、网络失败和超时都进入重试策略。
4. 重试耗尽后进入死信队列与人工处理页面。
5. 接收方必须按 `event_id` 实现幂等消费。

系统采用“至少一次投递 + 接收方幂等”，不假设跨系统 HTTP 调用可以做到恰好一次。

## 6. 安全基线

1. 百应 `appKey`、`appSecret` 仅保存在后端 Secret 中。
2. ERP、CRM、百应分别使用独立密钥，不共享。
3. ERP/CRM 入站请求采用平台自定义 HMAC 签名，至少包含请求体摘要、时间戳和随机数；百应出站请求遵循官方 OAuth v2，Access Token 仅放在后端请求 Body 中。
4. 后端必须拒绝过期时间戳和重复随机数，防止重放攻击。
5. 日志禁止记录完整手机号、密钥、签名原文或敏感业务参数。
6. 管理员发布映射、重放回调、手动创建任务等操作必须写入审计日志。
7. 生产环境禁止在前端、URL 参数、浏览器存储和代码仓库中出现任何外部系统密钥。

## 7. 全局话术变量映射

映射详细规则见：[全局话术变量映射与巡检方案](./全局话术变量映射与巡检方案.md)。

本架构强制遵守：

1. 映射全局共用，不区分影楼。
2. 映射在创建任务之前完成、发布并处于可用状态。
3. 任务创建时锁定映射版本快照。
4. 百应变量新增、删除、漂移或同步过期时，不允许新任务或新名单导入。

## 8. 核心数据模型

```text
integration_client
- id
- system_type                 ERP | CRM | BAIYING
- client_name
- credential_reference
- status

integration_request
- id
- source_system
- external_request_id
- idempotency_key
- request_payload_reference
- status
- request_id

integration_event
- id
- event_id
- event_type
- target_system
- payload_reference
- status
- occurred_at

delivery_attempt
- id
- integration_event_id
- attempt_number
- request_at
- response_code
- response_body_reference
- error_message

dead_letter_event
- id
- integration_event_id
- final_error
- next_action
- resolved_at

task_mapping_snapshot
- task_id
- mapping_version_id
- variables_json
- mapping_rules_json
```

业务配置和关系数据存 PostgreSQL。文件、大报文、导入原文件、回调原文和导出文件存 R2，数据库仅保存对象引用与摘要。

## 9. 队列与重试规则

至少包含以下队列：

```text
variable-sync-queue      百应话术变量巡检
task-import-queue        客户名单批量导入
callback-delivery-queue  ERP / CRM 回调投递
dead-letter-queue        重试耗尽的失败消息
```

重试规则：

```text
初始重试：1 分钟
后续重试：指数退避
最大重试：5 次
耗尽处理：进入死信队列，等待人工查看或重放
```

重放操作必须创建新的 `delivery_attempt`，不得覆盖历史失败记录。

## 10. 部署与环境

```text
development  本地模拟、测试密钥、隔离数据库
staging      对接 ERP / CRM / 百应测试环境
production   正式接口、正式 Secret、生产数据库与队列
```

每个环境必须使用独立的数据库、队列、R2 Bucket、百应 AK、ERP/CRM 密钥和回调地址。

不得用生产密钥测试开发环境，也不得让测试环境访问生产回调地址。

## 11. 扩展策略

### 首期

```text
TypeScript + 独立 API + PostgreSQL + Queue + Cron + R2
```

覆盖映射配置、变量巡检、任务创建、名单导入、百应回调、ERP/CRM 回传和审计。

### 后续

1. 新增业务系统时，新增 `integration adapter`，不修改核心任务编排逻辑。
2. 通话明细、分析数据规模增长时，进入独立数据仓库或分析库，不污染核心事务库。
3. 权限变复杂时，增加独立身份认证与 RBAC 模块。
4. 对接量增长时，独立扩容队列消费者和回调投递服务。

## 12. 开发验收清单

- [ ] 前端不能访问百应、ERP、CRM 密钥。
- [ ] 所有 ERP/CRM 入站请求具备签名与幂等处理。
- [ ] 所有百应、ERP、CRM 出站调用均可追踪 `request_id`。
- [ ] 外部回调支持重试、死信与人工重放。
- [ ] 所有任务锁定映射版本快照。
- [ ] 百应变量巡检异常可阻断新任务与新导入。
- [ ] 所有数据库变更使用版本化迁移。
- [ ] 所有外部 API 均有 OpenAPI 文档和契约测试。
- [ ] 关键操作、失败原因和人工处理均保留审计记录。
